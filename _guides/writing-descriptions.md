You can write a flawless skill and never see it fire once. The description is
the gate, and most descriptions are written as labels rather than as triggers.

## The mental model

At any moment the model sees a list of skill names and descriptions, and the
user's message. It's doing a matching problem: *does anything here apply?*

Your description isn't documentation. It's the argument for why this skill is
relevant right now.

## The formula

Two sentences:

1. **What it does** — the artifact and the operation.
2. **When to use it** — the situations, phrased the way a user would phrase them.

```yaml
description: >-
  Builds a chronological incident timeline from logs, deploy history, alerts,
  and chat transcripts. Use when the user is writing a post-mortem, doing
  incident review, or asking what happened during an outage.
```

The second sentence is what does the work. Note that "asking what happened
during an outage" doesn't contain the word *timeline* at all — that's the
point. Users describe their problem, not your solution.

## Use their words, not yours

Write down how someone would actually ask, then make sure those phrasings are
represented:

| You'd call it | They'd say |
|---|---|
| Atomic commit decomposition | "clean up my commits" |
| Coverage gap analysis | "what needs tests?" |
| Tabular data normalisation | "this spreadsheet is a mess" |
| Chronological event reconstruction | "what happened last night?" |

You don't need every synonym — you need the vocabulary space to overlap.

## Failure modes

**Too vague.** `Helps with documents.` Which documents? Doing what? Competes
with every other skill and wins nothing.

**Too narrow.** `Extracts tables from PDFs generated by Tableau Server 2023.2.`
Now it only fires when someone names the tool, which they won't.

**Describes the implementation.** `Uses pdfplumber and pandas to process PDF
files.` The model doesn't care what's inside. It cares what problem this solves.

**Missing the trigger sentence entirely.** The single most common mistake. If
your description has no "use when," go add one.

## Overlap between your own skills

Once you have a dozen skills, they start competing with each other. Two fixes:

**Draw the boundary explicitly.**

```yaml
# in pdf-form-filler
description: >-
  Fills or extracts values from fillable AcroForm PDFs. Use when the PDF has an
  interactive form layer. For scanned documents or text extraction from static
  PDFs, this is not the right skill.
```

**Or merge them.** Two skills that are hard to tell apart in a description are
usually one skill with a branch in the procedure.

## Test it properly

Write five phrasings a real user would use. Include at least two that don't
contain your skill's obvious keywords. Start clean sessions and try each one.

Under four out of five, the description is the problem — not the body.

Then try three phrasings that *shouldn't* trigger it. A skill that fires on
everything is as broken as one that never fires, just more annoying.

## A quick before/after

Before:

```yaml
name: release-notes-writer
description: Generates release notes.
```

After:

```yaml
name: release-notes-writer
description: >-
  Writes user-facing release notes from a git commit range, translating commit
  subjects into changes users will notice. Use when the user is cutting a
  release, preparing a changelog, tagging a version, or summarising what
  shipped since the last release.
```

Same skill. The second one actually runs.
